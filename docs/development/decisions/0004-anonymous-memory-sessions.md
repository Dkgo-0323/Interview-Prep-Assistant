## 场景与选择

两位访客不能共用JD、简历、报告或题目；同一访客分析中换资料，旧结果不能覆盖新输入。单独做身份隔离会遗留异步写回风险，因此一起处理。匿名Cookie是访客持有的随机凭证，不是实名账号，也不提供跨设备找回。

使用不透明HttpOnly Cookie，正文只含随机ID；原始资料/结构化结果保存在服务端单个进程内。闲置30分钟过期，最多100会话，参数可配置；刷新可恢复，重启丢失；满额拒绝新会话，不驱逐仍有效的访客。清除资料保留当前会话身份。空闲清理在后续会话访问/创建时惰性执行，不承诺到期瞬间清零进程内存。

未选择Redis/数据库：当前确认不要求重启恢复或多实例，新增服务会增加运行、隐私保留和迁移维护成本。以后若改变这两个需求，需另行设计和确认，不把本实现部署成多worker共享存储。未选择自动排队/合并：明确忙时提示比维护任务调度状态简单。

## 约束与后果

- 前端先共享一次初始化请求，再发并行上传；REST带credentials，EventSource带withCredentials。前后端本机地址使用同一主机名；CORS允许确切前端origin。浏览器Cookie策略可能限制跨站部署，因此公网域名/HTTPS方案仍需部署阶段验收。
- 重传、清除和重分析推进资料版本；操作取输入快照，线程完成后核对会话存活及版本才发布。过期/重启返回410；旧结果或同类任务占用返回409（SSE已开始则发终止error事件）。缺资料返回400，无缓存404，满会话503。
- 同类操作占用直到真正结束；取消HTTP等待不会停止同步供应商线程。取消后的结果不会发布，忙槽随线程完成释放，不宣称节省已发生的真实用量。
- 上传还有分文件序号，防止清除或较新同类上传后，较早的上传解析结果晚到覆盖。JD/简历并行上传可以各自完成。
- 健康检查不分配会话、不暴露资料键名；API响应no-store。画像仍未开放，历史占位接口仅接入身份隔离，不扩展画像能力。
