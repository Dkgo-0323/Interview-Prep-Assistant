# 长期开发协作入口

目标：将本仓库建设为适合 Python 后端、AI 应用、AI 全栈校招求职、可稳定在线演示的工程项目。以实际业务链路和可验证成果决定技术投入。

## 阅读顺序与事实标准

1. 读取适用的 `AGENTS.md`、根目录 `README.md` 和 `Architecture.md`。当前主链路是 Next.js → FastAPI → Qwen；Streamlit 是保留的原型。
2. 阅读 [status.md](status.md)、[roadmap.md](roadmap.md)、[backlog.md](backlog.md)、最近的 [daily](daily/) 和 [decisions](decisions/README.md)。
3. 检查当前代码、分支、HEAD、未提交改动、近期提交、相关聊天与 worktree，再判断上次任务是否完成。代码与本次实际验证优先于文档描述；历史分支、残留 `.pyc`、旧报告不是当前能力证据。
4. 按 [每日模板](templates/daily.md) 落盘规划，然后在当次新聊天讨论。

所有日期与更新时间使用 Asia/Shanghai。测试必须记录实际命令、环境、日期、退出结果及边界；历史结果明确标注历史。无法读取的 JD、未知发布时间、未知在招状态、无法访问的开源版本均如实记录，不用猜测补齐。

## 每日调研与规划

2026-10-20 用户反馈后采用的粒度：阶段总量与当天范围分开。每天默认只推荐一个约 1–3 有效人时的主任务（含实现、必要验证与回填），最多一个非默认的可选小任务；超过 3h 继续按可独立验收的边界拆分。阶段可以跨天，不把 10–18h 的阶段包当作一次每日任务或要求用户一次批准整个阶段。已确认未完成的增量优先接续。提交数量不反向驱动扩 scope 或机械拆分，小增量不足原 4–5+ 提交期望时如实说明。用户对粒度的反馈不等于批准具体功能或技术选型。

- 尽量核验 2–3 个企业官方岗位：直接来源、岗位名称、届别、校招/实习/社招、发布时间、访问日期、明确技能要求和在招可信边界。正文不可读时单独标注，搜索摘要不能当成完整岗位要求。
- 研究 1–2 个优质相关 GitHub 项目：仓库、具体模块或文件、版本或提交、访问日期、可借鉴实践、适用缺口、成本与替代方案。不要以名称、star 数代替研究。
- 将证据映射到本仓库缺口，形成优先级、任务范围、人时估算、依赖、验收和拟定提交边界。数量不足时解释原因，质量优先。
- 先写当天 daily，再同步 status、roadmap、backlog。已有同日文档只追加带时间的更新，保留原始快照、决策和回填；最新摘要可同步更新，历史记录不删除。

## Git 与质量

以每天 4–5 个或更多有价值的 GitHub 提交为目标，按独立且可验证的增量拆分，不空提交、不机械拆分。没有足够独立成果或用户尚未确认时，记录实际数量及原因。

方案确认后，在确认范围内完成适当检查、必要测试和说明，只显式暂存本次文件。检查通过后推送现有授权远程分支；每次核验分支、上游、远程和访问结果，不强推、不重置、不清理他人改动，不将 push 失败写成完成。新远程或明显分支范围变化先讨论。付费资源/模型调用、凭据配置及正式发布须先准备具体可审阅方案，再取得必要确认。

本仓库整个测试目录含真实模型调用，禁止当作纯离线回归盲跑。优先使用 `python scripts/check_backend.py` 的审阅清单；已修复解析器工厂测试替身，实际结果见 status。修改前端代码前须遵守 `frontend/AGENTS.md`，阅读安装版本的相关 Next.js 指南。

S1 新入口与 CI 细节见 [质量门禁](quality-gates.md)；测试修复和实际验证结果以最新 status/daily 为准。

## 回填与跨聊天交接

每个有意义的增量结束，以及完成、暂停、受阻时，都在当天 daily 追加：用户确认范围与出处、文件/改动、验证命令/环境/结果、未验证项及原因、SHA/推送、可演示成果、阻碍和下一步。同步 status、roadmap、backlog，重要技术决策写 decisions。未执行、未完成、未推送不得标完成。

新聊天可从以下消息开始：

> 请读取 docs/development/README.md、status.md、roadmap.md、backlog.md、最近 daily 和 decisions，核对代码/Git 与确认出处后，继续已确认未完成的任务。保留未提交改动，先报告冲突与范围变化。

文档会保留在当前工作区供下次本地任务读取；提交与推送的实际进展以 daily/status 为准。跨机器或新 worktree 接续前须核对分支与同步状态。
